WAMS Synchrophasor Monitor

Wide-Area Monitoring System — IEEE C37.118.2-2011 • DST-FIST MicroSmartGrid Lab

System Walkthrough

Follow each stage from hardware simulation to live cloud dashboard in sequence.

1
Proteus Digital Twin Simulation
A 4-bus MicroSmartGrid is simulated in Proteus ISIS using Arduino Uno firmware (.hex) flashed onto virtual microcontrollers. Each bus simulates a PMU: voltage phasors, current phasors, frequency, ROCOF, and power quantities are computed in real-time and printed as compact JSON to Proteus Virtual Terminal windows at 10 frames/second (100 ms period).
Proteus ISIS Arduino Uno Virtual Terminal 10 Hz
2
Screen OCR Capture (pmu_ocr)
A Python process (pmu_ocr/main.py) runs on the same Windows PC as Proteus. It uses mss to capture the screen region of each Virtual Terminal at 200 ms intervals. When pixel content changes, Tesseract OCR extracts the JSON text. The parser reconstructs the frame, correcting common OCR misread characters (e.g. 1→i, ;→:, 5→s). A duplicate-frame filter rejects re-reads of the same frame.
Python 3 mss (screen capture) Tesseract OCR JSON Reconstruction
3
Schema Transformation & Validation
The raw OCR dict (short keys: id, seq, v, va, i, ia, f…) is validated by validator.py: field presence, type coercion, frequency range (40–60 Hz), and microsecond bounds are checked. It is then transformed by forwarder.py into the full IEEE C37.118-aligned schema expected by the Render backend: long field names, nested objects, api_key, and station tag added.
validator.py forwarder.py Schema mapping Duplicate detection
4
HTTP POST to Render Cloud Backend
Each validated frame is sent as a non-blocking daemon-thread HTTP POST to https://pmu-backend-ury8.onrender.com/api/pmu-data with Content-Type: application/json. The backend authenticates via the api_key field (checked against the DEVICE_API_KEY environment variable). Frames from all 4 PMUs arrive independently and are stored immediately to the time-series database.
HTTPS POST API Key Auth Non-blocking thread Render Cloud
5
Node.js Backend — Storage & Real-Time Fanout
The Node.js / Express server (server.js) receives the POST, validates and flattens all fields against FIELD_SPEC in src/db.js, then writes a time-series point to InfluxDB Cloud (AWS us-east-1). Simultaneously, the latest frame is broadcast to all connected browsers via Socket.IO on the pmu:update event. The in-memory latest-state store means the REST API (/api/latest) always responds with zero DB latency.
Node.js Express InfluxDB Cloud Socket.IO Render
6
Browser Dashboard — Live Rendering
This dashboard (public/index.html + app.js) connects to the server via Socket.IO WebSocket. On each pmu:update event, the relevant PMU card is re-rendered: status badge, phasor values, frequency, power quantities, and alarm detection. Charts are fetched from /api/history?pmu_id=… on demand. A staleness detector runs every 5 seconds — if no frame arrives within the threshold (default 30 s), the PMU is marked STALE. Cold-start reconnect logic with exponential back-off handles Render free-tier spin-up delays.
Socket.IO WebSocket Canvas Charts Staleness Detection Cold-Start Retry

Dashboard Status Indicators

ONLINE
Receiving frames within the staleness threshold (default 30 s). Data is fresh and valid.
STALE
Last frame was received but no new data has arrived within the threshold. PMU may be slow or network interrupted.
OFFLINE
No frame ever received, or backend is unreachable. PMU device is not transmitting.
ALARM
A telemetry threshold has been breached: frequency deviation >±0.5 Hz, voltage <200 V or >260 V, or ROCOF >±1 Hz/s.
